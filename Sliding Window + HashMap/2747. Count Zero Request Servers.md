# 2747. Count Zero Request Servers

**Problem Link:** [LeetCode 2747 - Count Zero Request Servers](https://leetcode.com/problems/count-zero-request-servers/description/)
**Difficulty:** Medium
**Tags:** `Array`, `Hash Table`, `Sliding Window`, `Sorting`

---

## 📝 Problem Statement

You are given an integer `n` denoting the total number of servers and a 2D 0-indexed integer array `logs`, where `logs[i] = [server_id, time]` denotes that the server with id `server_id` received a request at time `time`.

You are also given an integer `x` and a 0-indexed integer array `queries`.

Return a 0-indexed integer array `arr` of length `queries.length` where `arr[i]` represents the number of servers that did not receive any requests during the time interval `[queries[i] - x, queries[i]]`.

*Note that the time intervals are inclusive.*

---

## 🚀 Examples

### Example 1

**Input:** 
`n = 3`, `logs = [[1,3],[2,6],[1,5]]`, `x = 5`, `queries = [10,11]`
**Output:** 
`[1,2]`
**Explanation:** 
- For `queries[0]`: The servers with ids 1 and 2 get requests in the duration of `[5, 10]`. Hence, only server 3 gets zero requests.
- For `queries[1]`: Only the server with id 2 gets a request in duration of `[6, 11]`. Hence, the servers with ids 1 and 3 are the only servers that do not receive any requests during that time period.

### Example 2

**Input:** 
`n = 3`, `logs = [[2,4],[2,1],[1,2],[3,1]]`, `x = 2`, `queries = [3,4]`
**Output:** 
`[0,1]`
**Explanation:** 
- For `queries[0]`: All servers get at least one request in the duration of `[1, 3]`.
- For `queries[1]`: Only server with id 3 gets no request in the duration `[2, 4]`.

## ⚠️ Constraints

- `1 <= n <= 10^5`
- `1 <= logs.length <= 10^5`
- `1 <= queries.length <= 10^5`
- `logs[i].length == 2`
- `1 <= logs[i][0] <= n`
- `1 <= logs[i][1] <= 10^6`
- `1 <= x <= 10^5`
- `x < queries[i] <= 10^6`

---

## 💡 Approach & Explanation

### The Challenge
A brute-force approach would be to iterate through the entire `logs` array for every single query to check which servers fall within the window `[query_time - x, query_time]`. With up to $10^5$ queries and $10^5$ logs, this $O(Q \times L)$ time complexity would lead to a Time Limit Exceeded (TLE) error.

### The Optimized Solution: Sliding Window
The core variable in this problem is **time**. By organizing our data chronologically, we can process it highly efficiently using a **Sliding Window**.

1. **Sort the Data:** 
   - First, sort the `logs` array based on their timestamps in ascending order.
   - Second, sort the `queries` array in ascending order. However, since we need to return the answer array matching the original order of queries, we must pair each query with its original index before sorting.

2. **Define the Window:**
   - We maintain a window using two pointers: `i` (left edge for shrinking) and `j` (right edge for expanding). 
   - We also maintain an `unordered_map` to track the frequency of unique servers receiving requests within our current window.

3. **Slide the Window Across Queries:**
   - Iterate through the sorted queries. For each query, the valid time interval is `start = query_time - x` to `end = query_time`.
   - **Expand:** Move the right pointer `j` forward, adding servers to our map as long as their log time is $\le$ `end`.
   - **Shrink:** Move the left pointer `i` forward, removing servers from our map if their log time is $<$ `start`. If a server's frequency drops to 0, completely erase it from the map.
   - **Calculate Result:** The `map.size()` now represents the exact number of *unique* servers that received a request in the valid time window. The number of servers that received *zero* requests is simply the total servers minus the active servers (`n - map.size()`). We store this result at the query's original index.

## 💻 Solution Code

```cpp
// Intuition: To efficiently find the number of inactive servers in a given time window for multiple queries, we can use a sliding window approach. Sorting both logs and queries by time allows us to slide a single window across the timeline rather than re-evaluating from scratch for each query.
// Approach: 
// 1. Sort the `logs` array based on the timestamp.
// 2. Pair each query with its original index and sort these pairs by the query time.
// 3. Use two pointers (`i` and `j`) to maintain a sliding window of valid logs for the current query's time range `[query - x, query]`.
// 4. Expand the right pointer `j` to include all logs that occurred on or before the current query's end time. Keep track of server frequencies using a hash map.
// 5. Shrink the left pointer `i` to exclude logs that occurred before the current query's start time. Remove servers from the map if their frequency drops to 0.
// 6. The number of active servers is the size of the hash map. The answer for the query is `n - map.size()`.
// Time Complexity: O(m log m + q log q), where m is the number of logs and q is the number of queries. Sorting takes the most time; the sliding window processes each log at most twice O(m).
// Space Complexity: O(m + q) auxiliary space for storing the query pairs with their original indices and the hash map for unique active servers.

class Solution {
public:
    vector<int> countServers(int n, vector<vector<int>>& logs, int x, vector<int>& queries) {
        int m = logs.size();

        // Custom comparator to sort logs based on time in ascending order
        auto lambda = [](vector<int>& vec1, vector<int>& vec2) {
            return vec1[1] < vec2[1];
        };

        sort(begin(logs), end(logs), lambda);

        int q = queries.size();
        vector<pair<int,int>> timeIndex(q);     // {time, original idx}
        
        // Store queries with original indices to place results correctly
        for (int i = 0; i < q; i++) 
            timeIndex[i] = {queries[i], i};

        // Sort queries by time
        sort(begin(timeIndex), end(timeIndex));

        unordered_map<int,int> mp;              // count unique servers in the window
        vector<int> result(q);

        int i = 0, j = 0;
        
        // Process each query
        for (auto [curtime, ind] : timeIndex) {
            int start = curtime - x;
            int end   = curtime;

            // right expand: add logs that are within the current end time
            while (j < m && logs[j][1] <= end) {
                mp[logs[j][0]]++;
                j++;
            }

            // left shrink: remove logs that fall behind the current start time
            while (i < m && logs[i][1] < start) {
                mp[logs[i][0]]--;
                if (mp[logs[i][0]] == 0) 
                    mp.erase(logs[i][0]);
                
                i++;
            }

            // mp.size() unique servers got requests. So, n - mp.size() did not recieve requests 
            result[ind] = n - mp.size();
        }

        return result;
    }
};

/*
*
* Dry Run
* n = 3, x = 5
* logs = [[1,3], [2,6], [1,5]]  -> Sorted logs: [[1,3], [1,5], [2,6]]
* queries = [10, 11]            -> Sorted queries: [{10, 0}, {11, 1}]
*
* Query 1: time = 10, index = 0, start = 5, end = 10
* - Expand j:
*   - j=0: logs[0][1] (3) <= 10. mp[1] = 1, j=1
*   - j=1: logs[1][1] (5) <= 10. mp[1] = 2, j=2
*   - j=2: logs[2][1] (6) <= 10. mp[2] = 1, j=3
* - Shrink i:
*   - i=0: logs[0][1] (3) < 5. mp[1] = 1, i=1
*   - i=1: logs[1][1] (5) >= 5. Stop shrinking.
* - Active servers: mp.size() = 2 (servers 1 and 2)
* - Zero request servers = 3 - 2 = 1. result[0] = 1
*
* Query 2: time = 11, index = 1, start = 6, end = 11
* - Expand j:
*   - j=3 >= m. Stop expanding.
* - Shrink i:
*   - i=1: logs[1][1] (5) < 6. mp[1] = 0 -> mp.erase(1), i=2
*   - i=2: logs[2][1] (6) >= 6. Stop shrinking.
* - Active servers: mp.size() = 1 (server 2)
* - Zero request servers = 3 - 1 = 2. result[1] = 2
*
* Result = [1, 2]
*
*/
```

## 🔑 Key Insights
- **Pointer Monotonicity:** Because both `logs` and `queries` are sorted, the `i` and `j` pointers only ever move forward. This ensures that across all queries, the while loops execute at most `m` times collectively, preventing an $O(Q \times L)$ bottleneck.
- **Index Preservation:** We must remember to sort the queries in pairs alongside their original indices, guaranteeing that `result[ind]` places the calculated answer precisely where the problem expects it.
