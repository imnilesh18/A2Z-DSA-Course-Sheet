# 877. Stone Game

**Difficulty**: Medium  
**Tags**: `Array`, `Math`, `Dynamic Programming`, `Game Theory`  
**Problem Link**: [LeetCode - 877. Stone Game](https://leetcode.com/problems/stone-game/description/)

## 📝 Problem Statement

Alice and Bob play a game with piles of stones. There are an even number of piles arranged in a row, and each pile has a positive integer number of stones `piles[i]`.

The objective of the game is to end with the most stones. The total number of stones across all the piles is odd, so there are no ties.

Alice and Bob take turns, with Alice starting first. Each turn, a player takes the entire pile of stones either from the beginning or from the end of the row. This continues until there are no more piles left, at which point the person with the most stones wins.

Assuming Alice and Bob play optimally, return `true` if Alice wins the game, or `false` if Bob wins.

---

## 📌 Constraints

* `2 <= piles.length <= 500`
* `piles.length` is even.
* `1 <= piles[i] <= 500`
* `sum(piles[i])` is odd.

## 💡 Approach & Explanation

This problem can be approached in two primary ways:

### Approach 1: Game Theory with Dynamic Programming (Min-Max)
Since both players play optimally, this is a classic Game Strategy problem. The fundamental rule of game strategy is:
* **When it's your turn, do your best.**
* **When it's your opponent's turn, expect the worst.**

Alice has two choices: take from the front (`piles[i]`) or take from the back (`piles[j]`).
If Alice picks from the front, the remaining array for Bob is `i+1` to `j`. Bob will play optimally, leaving Alice with the *minimum* possible future score. Thus, Alice's future options will be the minimum of what happens if Bob picks `i+1` or if Bob picks `j`.
Alice will evaluate both taking from the front and taking from the back, and choose the maximum of these two paths. We use memoization to avoid recomputing overlapping subproblems.

### Approach 2: Mathematical Observation (O(1))
By closely observing the game rules, we realize Alice always has a mathematical advantage:
1. Alice starts first.
2. The total number of piles is even.
3. The total sum of stones is odd (no ties).

Because Alice starts first, she has the power to take **ALL even-indexed piles** or **ALL odd-indexed piles**. For example, if she takes the 0th index, Bob is forced to choose between the 1st and the last (which is odd). No matter what Bob picks, he exposes another even index to Alice. 
Since the total sum of stones is odd, the sum of all even-indexed piles and all odd-indexed piles cannot be equal. Alice can simply calculate beforehand which parity (even or odd) yields a higher sum and commit to exclusively picking from that parity. Bob cannot stop her. Therefore, Alice **always** wins.

## 💻 Solution Code

### Brute-force / Standard DP Solution

```cpp
// Intuition: In a turn-based game where both players play optimally, we need to simulate choices. We aim to maximize Alice's score while expecting Bob to minimize her future gains.
// Approach: Use Recursion + Memoization. For the current range [i, j], Alice can pick piles[i] or piles[j]. Bob will then pick optimally from the remaining elements, leaving Alice with the minimum possible future score. We take the max of both scenarios.
// Time Complexity: O(n^2), where n is the number of piles, since there are O(n^2) possible subarrays represented by i and j.
// Space Complexity: O(n^2) for the 2D memoization table + O(n) for the recursion stack depth.
class Solution {
public:
    int n;
    int t[501][501]; // Memoization table to store max scores for subproblems
    int solve(vector<int>& piles, int i, int j) {
        // Base case: if pointers cross, no stones are left
        if(i > j)
            return 0;
        
        // Return pre-calculated result to avoid redundant work
        if(t[i][j] != -1)
            return t[i][j];
        
        /*
            That's how optimal game strategy works. Expect your opponent to be playing optimally
            -When it's your turn, do your best
            -When it's your opponent's turn, expect the worst (that's why min() is taken below)
        */
        
        // Alice takes front; Bob optimally leaves her with the minimum of future states
        int choose_i  = piles[i]  + min(solve(piles, i+2, j), solve(piles, i+1, j-1));
        
        // Alice takes back; Bob optimally leaves her with the minimum of future states
        int choose_j = piles[j] + min(solve(piles, i, j-2), solve(piles, i+1, j-1));
        
        // Alice takes the maximum outcome between choosing front or back
        return t[i][j] = max(choose_i, choose_j);
    }
    
    bool stoneGame(vector<int>& piles) {
        n = piles.size();
        memset(t, -1, sizeof(t)); // Initialize memo table with -1
        
        int sum = accumulate(begin(piles), end(piles), 0); // Total number of stones
        int alexScore = solve(piles, 0, n-1); // Max score Alice can achieve
        
        // Check if Alice collected more than half of the total stones
        return alexScore > sum/2;
    }
};

/*
*
* Dry Run
* piles = [5, 3, 4, 5]
* sum = 17, target to win = 17 / 2 = 8 stones.
* solve(0, 3) evaluates two branches:
* 1. Alice chooses piles[0] = 5. Remaining: [3, 4, 5]. 
*    Bob plays optimally to minimize Alice's next turn. Alice gets min(solve(2,3), solve(1,2)).
* 2. Alice chooses piles[3] = 5. Remaining: [5, 3, 4].
*    Bob plays optimally, Alice gets min(solve(0,1), solve(1,2)).
* The recursive calls eventually resolve, returning 10 as Alice's optimal score.
* Since 10 > 8, Alice wins (returns true).
*
*/
```

## 🧠 Key Insights
* **Min-Max Strategy:** In zero-sum games where players play optimally, simulating the opponent's best move means minimizing your future reward.
* **Parity Advantage:** When the number of elements is even, the first player can completely control the parity of the indices they pick from.
* **Avoid Over-engineering:** Sometimes a problem designed for Dynamic Programming has a hidden mathematical trick that bypasses complex algorithms entirely.
