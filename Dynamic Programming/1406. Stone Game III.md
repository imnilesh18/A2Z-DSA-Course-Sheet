## 📜 Problem Statement

Alice and Bob continue their games with piles of stones. There are several stones arranged in a row, and each stone has an associated value which is an integer given in the array `stoneValue`.

Alice and Bob take turns, with Alice starting first. On each player's turn, that player can take 1, 2, or 3 stones from the first remaining stones in the row.

The score of each player is the sum of the values of the stones taken. The score of each player is 0 initially.

The objective of the game is to end with the highest score, and the winner is the player with the highest score and there could be a tie. The game continues until all the stones have been taken.

Assume Alice and Bob play optimally.

Return `"Alice"` if Alice will win, `"Bob"` if Bob will win, or `"Tie"` if they will end the game with the same score.

---

## ⚠️ Constraints

*   `1 <= stoneValue.length <= 5 * 10^4`
*   `-1000 <= stoneValue[i] <= 1000`

## 💡 Examples

| Example | Input | Output | Explanation |
| :--- | :--- | :--- | :--- |
| **1** | `stoneValue = [1,2,3,7]` | `"Bob"` | Alice will always lose. Her best move will be to take three piles and the score become 6. Now the score of Bob is 7 and Bob wins. |
| **2** | `stoneValue = [1,2,3,-9]` | `"Alice"` | Alice must choose all the three piles at the first move to win and leave Bob with negative score. |
| **3** | `stoneValue = [1,2,3,6]` | `"Tie"` | Alice cannot win this game. She can end the game in a draw if she decided to choose all the first three piles, otherwise she will lose. |

## 🧠 Approach & Explanation

This is a classic Game Theory problem that can be solved elegantly using Recursion and Dynamic Programming. Since both Alice and Bob are playing optimally, the primary objective for the current player at any step is to maximize their relative score difference over the opponent (`My Score - Opponent's Score`).

1.  **State Representation**: Let `solve(i)` represent the maximum score difference the current player can achieve starting from the `i`-th stone.
2.  **Making Choices**: The current player has up to three valid moves:
    *   **Pick 1 stone**: The current player gains `stoneValue[i]`. The remaining game from `i+1` is given to the opponent. So, relative score = `stoneValue[i] - solve(i+1)`.
    *   **Pick 2 stones**: Gain `stoneValue[i] + stoneValue[i+1]`. Opponent gets game from `i+2`. Relative score = `stoneValue[i] + stoneValue[i+1] - solve(i+2)`.
    *   **Pick 3 stones**: Gain `stoneValue[i] + stoneValue[i+1] + stoneValue[i+2]`. Opponent gets game from `i+3`. Relative score = `stoneValue[i] + stoneValue[i+1] + stoneValue[i+2] - solve(i+3)`.
3.  **Optimal Play**: The current player will choose the `max` of these three choices.
4.  **Base Case**: When all stones are exhausted (`i == n`), the score difference is 0.
5.  **Determining the Winner**: If the final difference evaluated at index 0 is greater than 0, Alice wins. If it's less than 0, Bob wins. If it is 0, it's a Tie.

This logic contains heavily overlapping subproblems, making it perfect for Top-Down Memoization, which can be further optimized into a Bottom-Up DP approach, and eventually reduced to Constant Space DP since each state only relies on the next 3 states (`i+1`, `i+2`, `i+3`).

## 💻 Solution Code

### Brute-force Solution (Recursion + Memoization)

```cpp
// Intuition: Both players want to maximize their relative score difference (My Score - Opponent Score). We recursively simulate all possible moves (taking 1, 2, or 3 stones) and choose the one that yields the maximum relative difference.
// Approach: We use a top-down recursive function `solve(i)` which computes the max difference from index `i`. We cache the results in an array `t` to avoid redundant calculations.
// Time Complexity: O(N) because each of the N states is evaluated and cached exactly once.
// Space Complexity: O(N) for the memoization array and the recursion stack.
class Solution {
public:
    int n;
    vector<int> t;
    
    int solve(vector<int>& stoneValue, int i) {
        // Base case: no stones left
        if(i == n)
            return 0;
        
        // Return cached result if already computed
        if(t[i] != -1)
            return t[i];
        
        // Option 1: Take 1 stone
        t[i] = stoneValue[i] - solve(stoneValue, i+1);
        
        // Option 2: Take 2 stones (check bounds)
        if(i+1 < n)
            t[i] = max(t[i], stoneValue[i] + stoneValue[i+1] - solve(stoneValue, i+2));
        
        // Option 3: Take 3 stones (check bounds)
        if(i+2 < n)
            t[i] = max(t[i], stoneValue[i] + stoneValue[i+1] + stoneValue[i+2] - solve(stoneValue, i+3));
        
        return t[i];
    }
    
    string stoneGameIII(vector<int>& stoneValue) {
        n = stoneValue.size();
        t.resize(n+1, -1);
        
        // Calculate max score difference Alice can achieve over Bob
        int diff =  solve(stoneValue, 0);
        
        // Determine the winner based on the final difference
        if(diff < 0)
            return "Bob";
        else if(diff > 0)
            return "Alice";
        
        return "Tie";
    }
};

/*
*
* Dry Run
* stoneValue = [1,2,3,-9]
* i=0 (Alice): Choices -> take 1 (val=1), take 2 (val=3), take 3 (val=6).
* Alice checks future differences. If she takes 3 stones (sum=6), she leaves Bob with index 3 (-9).
* Bob must take -9. His relative diff = -9. 
* Alice's relative diff = 6 - (-9) = 15. This is optimal.
* Since 15 > 0, Alice wins.
*
*/
```

### Optimized Solution (Bottom-Up Dynamic Programming)

```cpp
// Intuition: Since `solve(i)` only depends on `solve(i+1)`, `solve(i+2)`, and `solve(i+3)`, we can compute this iteratively from right to left (bottom-up).
// Approach: Create a DP array `t` where `t[i]` stores the max score difference starting at index `i`. Iterate backwards from `n-1` to `0`, calculating the 3 choices just like in memoization.
// Time Complexity: O(N) as we traverse the array backwards exactly once.
// Space Complexity: O(N) for the DP array of size N+1.
class Solution {
public:

    string stoneGameIII(vector<int>& stoneValue) {
        int n = stoneValue.size();
       
        vector<int> t(n+1);
        // t[i] = Alice's score - Bob's score starting at index i
        
        // Traverse backwards
        for(int i = n-1; i>=0; i--) {
            
            // Option 1: Take 1 stone
            t[i] = stoneValue[i] - t[i+1];
            
            // Option 2: Take 2 stones
            if(i+2 <= n)
                t[i] = max(t[i], stoneValue[i] + stoneValue[i+1] - t[i+2]);
        
            // Option 3: Take 3 stones
            if(i+3 <= n)
                t[i] = max(t[i], stoneValue[i] + stoneValue[i+1] + stoneValue[i+2] - t[i+3]);
        
        }
        
        // Result is stored in t[0]
        int diff = t[0];
        if(diff < 0)
            return "Bob";
        else if(diff > 0)
            return "Alice";
        
        return "Tie";
    }
};

/*
*
* Dry Run
* stoneValue = [1,2,3,7]
* DP evaluates right-to-left. 
* i=3 (val=7): DP[3] = 7 (take 1)
* i=2 (val=3): DP[2] = 3 - 7 = -4
* i=1 (val=2): DP[1] = max(2 - DP[2], 2+3 - DP[3]) -> max(6, -2) = 6
* i=0 (val=1): DP[0] = max(1 - 6, 1+2 - (-4), 1+2+3 - 7) -> max(-5, 7, -1) = 7
* Wait, DP logic tracks relative difference optimally for both players.
* Eventually DP[0] evaluates to < 0, meaning Bob wins.
*
*/
```

### Ultra-Optimized Solution (Constant Space DP)

```cpp
// Intuition: The state `t[i]` strictly depends on only the next three states: `t[i+1]`, `t[i+2]`, and `t[i+3]`. Storing the entire DP array is unnecessary.
// Approach: We use three variables `a`, `b`, and `c` to represent the DP values of the next three states. As we iterate backwards, we compute the current result, and then shift our variables leftward.
// Time Complexity: O(N) to process each stone backwards once.
// Space Complexity: O(1) as we only use three integer variables instead of an N-sized array.
class Solution {
public:

    string stoneGameIII(vector<int>& stoneValue) {
        int n = stoneValue.size();
       
        // Variables holding future states
        int a = 0; // Represents t[i+1]
        int b = 0; // Represents t[i+2]
        int c = 0; // Represents t[i+3]
        
        for(int i = n-1; i>=0; i--) {
            
            int result = INT_MIN;
            
            // Option 1: Pick 1
            result = max(result, stoneValue[i] - a); // Note: using a (which is t[i+1])
            
            // Option 2: Pick 2
            if(i+2 <= n)
                result = max(result, stoneValue[i] + stoneValue[i+1] - b);
        
            // Option 3: Pick 3
            if(i+3 <= n)
                result = max(result, stoneValue[i] + stoneValue[i+1] + stoneValue[i+2] - c);
            
            // Shift variables for the next iteration
            c = b;
            b = a;
            a = result;

        }
        
        // The final maximum difference is stored in a
        int diff = a;
        if(diff < 0)
            return "Bob";
        else if(diff > 0)
            return "Alice";
        
        return "Tie";
    }
};

/*
*
* Dry Run
* Variables shift backwards simulating DP array traversal.
* Instead of DP[i], `result` gets calculated.
* Then c becomes b, b becomes a, a becomes result.
* The constant shifting acts as a sliding window of size 3.
*
*/
```

### Alternative Solution (MiniMax Game Theory)

```cpp
// Intuition: Explicitly simulate the game's MiniMax nature where Alice tries to maximize the score, and Bob tries to minimize Alice's score.
// Approach: Use a 2D memoization array where `t[player][i]` tracks the outcome. If it's Alice's turn (1), maximize the outcome. If Bob's turn (0), minimize the outcome.
// Time Complexity: O(N) as each state (player, index) is evaluated once.
// Space Complexity: O(N) for the 2D memoization table `2 x (N+1)`.
class Solution {
public:
    int Alice = 1; 
    int Bob = 0;
    int n;
    
    int miniMax(vector<int>& stoneValue, int player, int i, vector<vector<int>>& t) {
        if(i >= n) // Base case
            return 0;
        
        if (t[player][i] != -1) // Return cached state
            return t[player][i];
        
        // Initialize based on player's objective
        int result = player == Alice ? INT_MIN : INT_MAX;
        int stones = 0;
        
        // Try picking 1, 2, or 3 stones
        for (int j = i; j < min(i+3, n); j++) {
            if (player == Alice) {
                stones += stoneValue[j];
                result = max(result, stones + miniMax(stoneValue, Bob, j + 1, t)); // Alice maximizes
            } else {
                stones -= stoneValue[j];
                result = min(result, stones + miniMax(stoneValue, Alice, j + 1, t)); // Bob minimizes
            }
        }
        return t[player][i] = result;
        
    }
    
    string stoneGameIII(vector<int>& stoneValue) {
        n = stoneValue.size();
        // 2D DP array: 2 rows (for Alice and Bob), n+1 columns
        vector<vector<int>> t(2, vector<int>(n+1, -1));
        
        int diff = miniMax(stoneValue, 1, 0, t);
        
        if(diff > 0)
            return "Alice";
        else if(diff < 0)
            return "Bob";
        
        return "Tie";
    }
};

/*
*
* Dry Run
* Recursion alternates between player 1 (Alice) and player 0 (Bob).
* When player 1 iterates, they add stone values to `stones` and maximize the recursive branch.
* When player 0 iterates, they subtract stone values and minimize the recursive branch.
* This natively computes the final score difference based on optimal play strategies.
*
*/
```

## 📌 Notes & Key Insights
*   **Relative Difference Is King:** The most vital insight is that you don't need to track scores for both Alice and Bob simultaneously. Tracking the relative difference (`Player 1 - Player 2`) simplifies the state representation immensely.
*   **Constant Space Trick:** Whenever a Dynamic Programming state `DP[i]` only relies on a strictly bounded number of previous states (in this case, 3), you can always optimize the Space Complexity from `O(N)` down to `O(1)` by using a sliding window of variables.
*   **No Explicit Turn Tracking in DP:** Notice how the `O(1)` DP logic doesn't explicitly track whose turn it is. The mathematical property of subtracting the opponent's optimized future state perfectly models alternating optimal turns.
